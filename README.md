# Project Kickoff

一个用于 Codex 的项目启动 Skill，帮助你在开始实现之前，把模糊想法逐步收敛为有依据、范围明确、可验收、可交接的启动方案。

它重点解决的问题是：需求过早定案，项目做到一半才发现目标、使用场景或首版范围理解错了。

## 它做什么

Project Kickoff 会先了解项目起点，再通过一次一个关键问题的方式确认：

- 项目是为了学习、作品展示、实际使用，还是几者的组合
- 目标用户、具体使用场景和当前做法
- 首版范围、非目标、主要流程和重大约束
- 可观察的验收条件，以及仍需实验或原型验证的假设
- 分阶段的目标、依赖、交付物、验收方式和停止点

它还可以在需要时协调 UI 原型交接，并在获得明确授权后搭建能启动、能走通一个最小流程的工程。

## 核心原则

1. 先调查，再提问。区分代码和文档中的事实、用户目标、建议与未验证假设。
2. 一次只解决一个会改变方案的关键问题，不用固定问卷填满流程。
3. 把“智能”“方便”“快速”等抽象目标转成用户操作和可观察结果。
4. 说明方案取舍，但用户理解代价后坚持的选择会被记录，不反复劝退。
5. 不能靠讨论确定的内容进入验证任务，不能把猜测写成已确认事实。
6. 需求确认、文档编写、代码搭建、测试和发布是不同授权范围。
7. 只在当前目标需要时生成文档和工程，不创建未来功能的空目录。

## 典型工作流

```text
调查项目起点
    ↓
确认目标与具体场景
    ↓
收敛首版范围、流程和验收
    ↓
处理实验或 UI 原型等关键不确定性
    ↓
写入启动记录、需求说明和阶段计划
    ↓
（单独授权后）搭建最小可运行工程
    ↓
交接证据、未决项和下一阶段入口
```

每个主题收敛后，记录决定、理由、状态和待验证项。状态至少区分：`已确认`、`建议`、`默认`、`待验证`、`已替代`。

## 何时使用

适合：

- 从一个想法开始新软件项目
- 为已有项目规划一个较大的新方向
- 需求、范围、交互或验收仍存在高影响不确定性
- 需要把讨论整理成可以交给后续开发的文档

不适合：

- 普通 Bug 修复或单文件修改
- 执行已经确认的实现计划
- 只问一个技术概念
- 只修改 README、文案或格式

## 如何调用

在 Codex 中使用：

```text
使用 $project-kickoff，一次一个关键问题，帮我明确这个项目，先完成需求和分阶段计划，不写代码。
```

如果是已有项目，应同时说明项目路径或仓库位置。若已经有启动记录、需求文档或设计原型，Skill 会先读取并沿用已确认的内容，避免重复采访。

## 文档交付

根据项目实际需要，通常会形成：

- 启动记录：决定、理由、状态、讨论进度和授权边界
- 需求说明：目标、场景、范围、流程、非目标和验收
- 阶段计划：阶段目标、依赖、交付、验收和停止点
- 架构或项目规则：只有在实际复杂度需要时才添加

已有项目优先更新已有文档入口，避免产生互相矛盾的第二套资料。UI 原型是按需的验证环节；已有确认设计时直接引用版本，不强制重新设计。

## 权限与验证边界

确认需求不等于授权写代码。README、需求文档、自动检查、真实运行、UI 对照和安装交付分别代表不同层级的证据。

没有实际运行或测试时，结果会明确标为“未验证”；构建成功也不等于桌面运行或安装验收通过。提交、推送、安装和发布只在用户明确授权的范围内进行。

## Skill 结构

运行入口为 `SKILL.md`，参考资料按需放在 `references/`，界面展示信息放在 `agents/openai.yaml`。参考资料不会全部默认加载，以减少无关上下文。

## 当前状态

本仓库当前用于维护 Project Kickoff 的公开说明。Skill 源文件和安装包的验证记录保存在对应的本地 Skill 目录中；后续发布 Skill 包时，应同时检查入口文件、参考路径、自动发现配置和安装后的实际触发行为。
