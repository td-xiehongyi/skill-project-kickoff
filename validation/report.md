## 方法与证据边界

无 Skill 基线和有 Skill 对照分别由独立上下文执行。两者接收相同的十个独立案例，每案回答限制为 220 中文字，不修改文件、不调用真实提问工具。对照执行者只读取 Skill 及访谈、文档参考，没有收到判据或基线结果。

这些案例在各自一次运行中批量提供，所以并非十次独立重复采样。它们验证的是给定情景下的下一条回答，不证明长期稳定性、自动发现、真实工具问答或完整开发交付。另行使用隔离临时目录检查真实文档交接。

## 无 Skill 基线原文

1. 先把“智能”落到具体问题：你最想解决哪种混乱——下载文件太多、照片难找，还是文档分类费时？建议首版先做扫描、分类建议、操作预览、确认执行和撤销。需求明确后，再按“基础整理→AI 建议→体验完善”拆分计划。你主要整理什么文件、使用什么系统？

2. 可以，把“学会数据库和完整开发流程”作为主要目标。建议首版包含收支录入、分类、修改删除、按月汇总，再经历需求、数据库设计、实现、测试和交付。先确认使用场景：这是你一个人使用的本地工具，还是希望做成网页并支持登录？

3. 需求和验收条件已足够明确。预算建议暂按“无付费服务、无云资源，开发工时待估算”记录，不把它当作你已确认的预算。计划分三步：确定 CSV 字段及异常规则；实现只读导入、月份筛选和汇总；用两份样本核对结果并检查错误提示及源文件完整性。本阶段仅交付需求和计划。

4. 先记录现有冲突：PRD 限管理员上传，当前代码允许管理员和成员，而且该文件有你的未提交修改，不能据此认定成员权限已经确认。规划增加访客上传前，需要明确访客身份、大小与类型限制、审核和滥用防护。你希望访客直接上传，还是通过管理员发放的链接上传？现有文件保持不动。

5. 我可以给出暂定目标，但不能把未经使用验证的数字写成已确认需求。先设“每次 1 万条、常见操作 2 秒内”为待验证假设，并注明测试设备与数据格式尚未确定；首次样本测试后调整。这样可以继续完成计划，也避免后续把随手选的数字当作硬性承诺。

6. 已确认采用 SQLite，理由是学习数据库；这项决定不再展开讨论。接下来确认数据本身：首版需要记录哪些字段？建议从日期、金额、收入或支出、分类、备注开始，再决定是否需要修改、删除和按月统计。

7. 可以先写带决策点的计划：先确定预约对象、可预约规则及取消规则，再确定预约顺序，然后规划实现和验收。当前无法制作交互原型，我先用文字比较两条路径：“选服务→看可用时间→确认”与“选时间→看可用服务→确认”。哪条更符合你的用户习惯，将影响页面流程，暂不锁定。

8. 以已确认的设计 v2 为实现依据。计划分三步：完成 CSV 选择与解析；接入月份筛选及汇总表；按设计实现空、加载和错误状态。验收覆盖导入成功、切换月份、无数据和文件错误，并逐项核对 v2。先检查已有项目和 CSV 字段约定，再细化工作量与依赖，不重新设计页面。

9. 两台设备共享数据会改变 D1“离线单用户”和 D2“不做同步”的前提，需要更新这两项记录，并重估数据交换、冲突处理及验收范围。我们仍只做需求和计划。先确认“共享”的含义：手动导出导入即可，还是希望两台设备自动保持一致？

10. 可以，只修 README 的拼写错误。请指出需要改正的词或贴出对应那一行。

基线发现：案例 1 同时提出多个独立问题，并在关键场景未明时推荐首版功能和阶段；案例 2 也提前枚举功能；案例 3 用候选预算继续规划而没有解决用户提出的预算缺口。案例 5 已标明假设，不能把它记为“捏造已确认事实”的失败。其他多数边界在基线中已表现良好，不能声称全由新增 Skill 带来。

## 首轮有 Skill 回答原文

1. 我会用 project-kickoff 帮你逐步明确需求，再整理分阶段计划。“越智能越好”还不足以决定首版范围：你做这个软件，最优先是解决自己实际整理文件的问题，还是学习开发、做作品展示？

2. 已明确：这是学习项目，重点是数据库能力和完整开发流程，已有产品更好不影响这个目标。我会用 project-kickoff 继续收敛需求。你希望首先完成哪一个具体记账场景，例如记录日常消费后查看当月支出？

3. 现有信息已足够整理需求和计划，预算可先记为未定，不必为填表继续追问。需求按你给出的范围与验收保留。计划分三阶段：①本阶段整理需求、样本验收步骤和阶段边界；②获准后实现选择 CSV、月度汇总及错误提示；③用两份样本核对汇总，并验证错误文件不覆盖源文件。遇到付费选项再核对预算。本阶段止于文档。

4. 我会用 project-kickoff 先核对现状：PRD 声明仅管理员上传，但所给函数允许管理员和成员；该文件还有未提交改动，我会保留。单个函数尚不能证明完整上传流程。增加访客权限前，需要确定未来权限基线：你希望最终管理员、成员和访客都能上传吗？

5. 可以先交付条件性草案，但数据规模和速度没有使用证据，不能写成已确认事实。先增加一个小验证任务：用不同大小的样本测量处理时间，再结合真实文件确定性能验收值。样本大小只标为试验输入；功能范围可以定稿，依赖性能结果的部分保持待验证。

6. 好，沿用已确认的 SQLite 决定，理由是学习数据库；不再重开存储比较。接下来确认一个会影响数据结构的需求：首版的一笔收支记录，你需要保存哪些信息？

7. 我会用 project-kickoff 整理计划，预约顺序先标为待验证，它只阻塞相关交互实现。目前没有 ui-prototype 能力，可以先用文字流程比较，并准备后续原型交接说明。先确认具体场景：用户来预约时，通常已经选好了服务，还是主要想找到某个时间能约的服务？

8. 以你已确认的设计 v2 为实现依据，沿用 CSV 选择、月份筛选、汇总表及空、加载、错误状态。计划先对照 v2 整理交互与数据要求，再安排读取、筛选和汇总实现，最后核对样本结果及各状态是否符合设计。当前交付需求与阶段计划；尚未进行实现或运行验证。

9. “两台设备共享数据”改变了 D1 离线单用户、D2 不做同步的原有前提。我会保留旧决定及理由，新增变更记录，并重新评估受影响的需求和计划；当前仍限需求与计划。你说的共享，是手动导出后在另一台设备导入即可，还是需要两台设备自动保持最新数据？

10. 这个请求不需要启动项目规划。我会先定位 README 中的拼写错误，只修正该处，并保留其他内容和已有改动。

人工评估：案例 1、2、4–10 的下一条回答符合对应判据；案例 3 未通过，仍然回避了用户明确提出的预算缺口。这里的九案符合仅指单轮模拟；案例 10 没有实际定位或编辑 README，案例 9 没有实际更新文档。

修正：在访谈策略中要求先判断用户明确指出的缺口影响什么，不能仅以“不是阻塞项”或“避免填表”为由跳过。预算只是解释此问题的例子，并未增加所有项目都必须问预算的规则。
