# 文档与交接约定

在保存主题结论、编写正式文档、交接原型或工程时读取。文档为后续决策和执行服务，不要求固定数量。

## 选择位置与事实来源

先查项目已有入口和命名，原位更新对应文档，保留无关内容和用户改动。没有约定时采用 `docs/kickoff.md`、`docs/requirements.md`、`docs/roadmap.md`；用户指定路径优先。已有项目有多个启动方向时，沿现有主题目录组织，避免混写其他方向。

启动记录保存决定的状态、理由和讨论进度；正式文档保存当前需求和方案，并引用相关决定编号。不要在多个地方复制完整决定历史。架构、安全、部署文档仅在实际复杂度或风险需要时增加。

## 启动记录的最小内容

- 项目目的与本次范围；现有资料入口、相关实现证据及差异。
- 决定记录：稳定编号、内容、状态、理由或来源。状态使用“已确认、建议、默认、待验证、已替代”；未知需求不能仅因写入文件而升级状态。
- 变更时保留旧决定，记录替代关系和受影响需求、计划或设计；待确认变更不冒充已经生效。
- 当前停在哪个主题，下一步是什么，哪些未决问题会阻塞哪些阶段。
- 仅对阻塞性验证任务补充：执行方（可为待分配）、输入来源、最小验证办法、判断依据、最晚决策阶段，以及通过、失败、无结果三种处理。阈值未知时先验证如何确定阈值，不伪造承诺；到依赖阶段仍无结果时执行已授权降级方案，否则暂停依赖工作并交接该阻塞，无关工作可继续。
- 授权范围：当前可以讨论、写文档或搭建到哪里，以及现有授权依据。拟议的下一步单独列出。

每个主题收敛并确认后保存，不按每条消息刷文件。用户已明确确认的内容无需再问一次“是否保存”；用户要求不落盘、当前处于只读模式或写入不可用时，在对话里保留摘要并说明未保存。恢复时先核对文件与当前请求，避免只依赖对话记忆。

## 正式方案

| 产物 | 最少需要说明 |
| --- | --- |
| 需求说明 | 目的、目标用户与场景、核心流程、首版范围、非目标、重大约束、可观察的验收办法及未决项 |
| 阶段计划 | 每阶段目标、依赖、交付、验收方法与停止点；近期已授权阶段细化可执行任务；其他阶段保留概要 |
| 架构说明（按需） | 已选择的方案及原因、职责和数据流、必要接口与失败处理、已有项目兼容影响 |
| 项目规则（按需） | 文档入口、已确认且持续有效的开发约束、从实际配置核实的命令；详细内容用链接，不重复进度 |

验收描述采用“给定条件 → 用户操作 → 可观察结果 → 验证办法”，按任务需要写正常和重要失败路径。没有代码的项目不能声称命令已跑通；候选命令标为待验证，不作为已验证事实写入项目规则。

没有重大架构决策时，用需求或计划中的简短说明即可。项目规则不照搬其他项目的技术栈、审批条款或具体安全流水线。对安全、隐私、数据修改等约束，仅记录本项目实际决定和需求。

交付草案与确认正式方案是不同状态。尚未解决的关键问题要定位到受影响阶段；允许交付条件性计划，但不能用“文档齐全”掩盖实施尚未就绪。

## UI 原型接口

仅在 UI 不确定性影响需求或近期实现时准备交接。已有确认设计记录其可访问路径与版本；若缺少材料，说明缺口，不能仅凭版本名声称已检查设计。

交给原型工作的内容：目标用户、核心任务、已确认需求与约束、影响流程的未决问题、现有设计入口以及本次希望验证的判断。标明“探索方案”或“落实设计”：探索时提供候选假设、共同操作任务和比较依据；落实时提供可访问的设计版本及分项确认范围。仍缺失的业务事实不能伪装成已确认规则。

预期返回：可查看原型、评审编号及版本、关键交互与状态说明、模拟数据或未接入能力、分项确认状态及依据、新发现与受影响需求。交付完整性、运行检查、用户确认分别记录：探索草案可以已交付但尚未确认；缺失内容列明，不把部分确认升级为整版批准。

原型带来变化时，回到有关决定和需求确认，再修订受影响计划。不要为了让实现“符合设计”而静默修改已确认设计；保留版本依据和变更理由。原型的视觉确认不证明真实后端行为正确。

## 工程与最终交接

搭建授权需能确定范围与验收目标。已有授权够用时直接执行；不够时先展示具体提议，如可运行入口、一个最小流程、验证办法和停止点，再询问。不要在授权前建立框架作为“准备”。

交接时说明：完成内容与文件入口、已确认决定、未决项及影响、实际验证证据、下一阶段目标、授权边界。验证证据区分自动检查、实际运行、UI 对照与安装交付；不相关层级省略，相关但没做的标为未验证。构建成功不能代替运行验收。

交接后结束启动流程。下一阶段是建议，不自动成为授权；本 Skill 不接管长期进度维护。
